## как работает

PDF разбираю по страницам через pymupdf. Текст собираю сам из координат: что
на одной высоте, то одна строка, а между далеко стоящими кусками ставлю " | ".
Так строка таблицы не разваливается на отдельные ячейки, и модели видно, какое
число в какой колонке. Если на странице почти нет текста, значит это скан, его
распознаю через Vision на маке. Сканов немного, но Альфа 2024 целиком скан, и
на нее 18 вопросов в test. Все страницы лежат в data/pages.jsonl.

Для каждой страницы считаю эмбеддинг через сервис эмбеддингов курса, векторы в
data/page_vectors.npy. Считалось час из-за лимита 60 запросов в минуту, поэтому
закоммитил, чтобы при проверке не пересчитывать.

Поиск. Сначала по названию банка в вопросе беру только его отчеты, регулярки
не ошиблись ни разу ни на train, ни на test. Отчетам за нужный год и период
даю небольшой бонус. Дальше BM25 и косинус по эмбеддингам, ранги складываю
(RRF). Проверял на всем train, как часто нужная страница попадает в первые 6:
BM25 0.687, эмбеддинги 0.695, вместе 0.787.

Отвечает deepseek-flash, у нее два тула, search и answer. Она видит 6 найденных
страниц и сама решает, хватает их или надо поискать еще, со своим запросом и в
нужных отчетах (максимум два раза). В answer она указывает страницы, откуда
взяла ответ, они и идут в context. Иначе precision был бы маленький: показал 6
страниц, а нужна одна.

## langsmith

Эксперимент на том же test с трассами и метриками:
https://eu.smith.langchain.com/public/f6c5df14-bf4e-4840-9480-10bcb6377954/d

В трассе видно весь путь вопроса: rag, внутри каждый search и каждый вызов
модели. Это отдельный прогон, поэтому числа чуть другие, чем в Excel: recall
0.758, precision 0.793, answer 0.851, time 5.37. Разница в пределах шума,
заодно видно, что повторный прогон дает примерно то же самое.

Запуск: eval/evaluator_langsmith.py сам создает датасет из jsonl, если его нет.

```bash
LANGSMITH_TRACING=true LANGSMITH_API_KEY=... LANGSMITH_ENDPOINT=https://eu.api.smith.langchain.com \
  uv run python -m eval.evaluator_langsmith data/test.jsonl
```

## что пробовал

Отлаживал на 30 случайных вопросах из train. Только с BM25 вышло recall 0.738,
precision 0.767, answer 0.900. Ошибки были в основном от лишнего в ответе:
модель добавляла цифры за другие годы, и судья за это ставил 0. Попросил в
промпте отвечать только на вопрос. Еще один раз модель ответила текстом мимо
answer, теперь такой текст тоже засчитывается.

С эмбеддингами на тех же 30 вышло 0.677, 0.733 и 0.867, то есть на один
верный ответ меньше. На 30 вопросах это шум, а по поиску на всем train гибрид
лучше на 10 пунктов, так что оставил его.

Recall в целом ниже, чем мог бы быть, из-за разметки: одно и то же число часто
есть и в сводной таблице, и в примечании. Модель берет одно, в эталоне другое,
ответ при этом верный.

## eval

В eval/evaluator_excel.py добавил паузу перед вопросом, чтобы не упираться в 10
запросов в минуту у шлюза (пауза до старта таймера, в time не входит), и повтор
вызова судьи при 429. Модель и промпт судьи не трогал. Еще каждый вопрос
сразу пишется в outputs/, и если прогон упал (у меня один раз шлюз не ответил
за 2 минуты), повторный запуск продолжит с места остановки. Перед новым
прогоном эту папку надо удалить.

Время в основном это ответ шлюза, так что оно зависит от его загрузки. Мой
прогон был вечером в день дедлайна.

## запуск

Нужен uv и .env в корне с LLM_API_KEY и EMB_KEY.

```bash
uv sync
uv run python -m eval.evaluator_excel data/test.jsonl --output test_results.xlsx
```

PDF для этого не нужны. Идет около часа, все упирается в лимит шлюза.

Если хочется пересобрать индекс с нуля (только мак из-за OCR):

```bash
python -m zipfile -e data/reports.zip data/reports
uv sync --group parse
uv run python -m rag.parse
uv run python -m rag.index
```

Библиотеки: pymupdf, pyobjc для Vision, numpy, requests, openpyxl, langsmith.
